#+TITLE: C++ Style Guide

* Naming

** Core table

- Classes, structs, enums, concepts, using-aliases, template parameters :: PascalCase
- Namespaces :: PascalCase
- Functions and methods :: PascalCase
- Enum values :: PascalCase
- Local variables, including const :: camelCase
- Function parameters :: camelCase
- Class and namespace constants :: PascalCase
- Public fields / properties :: PascalCase
- Private instance members :: m_PascalCase
- Mutable static class members :: s_PascalCase
- Function-local statics :: s_camelCase
- File-scope mutable variables in .cpp :: s_PascalCase
- Global mutable variables :: g_PascalCase
- Acronyms :: all caps (HTTPServer instead of HttpServer)

** Prefix philosophy
- Bare PascalCase = immutable or public contract. Safe to use, no thinking required.
- m_ = instance state, internal. Makes side effects visible inside method bodies, exposes implicit this capture in lambdas, guards against shadowing. Plus autocomplete convenience.
- s_ = shared mutable state. A warning about danger.
- g_ = the same thing, but at global scope.

Prefixes do NOT stack: a variable carries exactly one marker.
The marker is chosen by what matters most for the reader to know; a conflict is most likely between m_ and s_, and in such cases pick s_.

** Getters and setters

- Getter :: just Name(), no Get prefix
- Private field with a getter :: m_Health + Health()
- Getter+setter pair :: allowed only when invariants need validation — Health() and SetHealth(); usually a public field is better
- Expensive computations :: a verb Compute/Build/Create instead of a bare name. A bare Health() implies cheap O(1) access.
- Boolean predicates :: Is/Has/Can
- On* :: event handlers, for extension via inheritance or callbacks

** Forbidden and anti-names

- Leading underscore forbidden :: _Foo, __foo are reserved by the standard
- Anti-names, a decomposition signal :: Helper, Utils, Common, Data, Info
- Interfaces :: no I-prefix, plain PascalCase.

* Arithmetic types

Standard int/float are not used — the size must be visible from the name. Aliases are declared once per project and reused everywhere:

#+begin_src cpp
using u8 = std::uint8_t;
using i32 = std::int32_t;
using f32 = float;
using usize = std::size_t; // for stl compatibility
#+end_src

- bool and char are used as-is

* Class skeleton

Explicit sections. Empty sections are omitted. The reader moves from contract to internals.

1. public: nested types (enums, usings, structs)
2. public: class constants
3. public: factories
4. public: constructors, assignment, destructor
5. public: properties — statics first, then regular ones
6. public: queries (const, read state)
7. public: commands (mutate state)
8. protected: hooks for derived classes, virtual, On*-handlers
9. private: private constants
10. private: private helpers
11. private: private statics
12. private: data

Rules:

- Protected fields are FORBIDDEN entirely. Methods and hooks only.
- [[nodiscard]] is optional; writing it is good practice, but use it sparingly so code stays readable.
- enum class with an explicit underlying type.
- Definition order in .cpp mirrors the declaration order in .h.

* struct vs class

- struct :: passive aggregate: all fields public, no invariants
- class :: there are invariants, logic, or hidden state
- Methods in a struct are not forbidden as long as data stays open and integrity needs no protection

* Inheritance

Default — do not inherit. Composition and data-over-data by default. Inheritance is a deliberate exception.

** Legitimate cases

- Template method :: the base owns the algorithm, the derived class overrides protected On*-hooks.
- Interface at the boundary :: pure virtual contract, when there are multiple implementations and the choice is made externally (render backends, platforms). Not for hot paths.

** No polymorphism on the hot path

In cold paths performance is not a concern: roughly speaking, a virtual call 3-4 times per frame is fine. But if you walk over an array of entities calling a virtual method through a pointer in every slot, it has to be reworked.

** Spectrum of entity representation

From preferred to forbidden:

1. Data + systems / DOD :: entity is an index/handle, components are POD aggregates in dense arrays, behavior is free-function systems over ranges.
2. Component composition (Object + components) :: an aggregator object holds component classes with virtual methods.
3. Inheritance tree :: Entity -> Character -> Enemy -> Boss. FORBIDDEN: combinatorial growth of the hierarchy, fragile base, behavior smeared around and invisible as a whole, orthogonal properties requiring multiple inheritance, data scattered across levels against the cache.

** Forbidden outright

- Diamonds and virtual inheritance
- A single god-root for all engine classes
- private/protected inheritance

** RTTI and downcasting

We compile with -fno-rtti. dynamic_cast and typeid are forbidden. Need a concrete type — a kind tag in the data + assert on downcast, or a switch over the tag, which is usually what was needed anyway.

** final

Leaf classes with virtual functions, as well as classes never meant to be inherited from, are marked final: free devirtualization plus an honest contract "do not derive from me".

* Global variables

Discouraged, but not forbidden.

When used, the following are mandatory:

1. g_PascalCase prefix for globals, s_PascalCase for statics
2. A justification comment at the declaration site: why it cannot be passed explicitly.
3. Scope kept as narrow as possible.

* Lambdas

- Explicit captures only: [x, &out]. [=] and [&] are FORBIDDEN
- this is captured explicitly too: [this], or [id = m_ID] when you need a field's value
- Prefer creating and using a lambda right away — an overgrown or reused lambda is a candidate for extraction into a function

* Namespaces

- using namespace is banned everywhere, including function bodies. Use an alias instead: namespace fs = std::filesystem;.
- Internal linkage in .cpp :: anonymous namespace, not static
- Nested namespaces :: allowed and preferred over nested blocks.

* Exceptions and asserts

No hard ban on exceptions, but we avoid them; compile with -fno-exceptions if desired.

- Expected failures :: std::optional / std::expected
- Programmer bugs :: assert — often and mercilessly; side effects inside assert are forbidden.
- static_assert :: type and size invariants, free at compile time

* Initialization

- Header initialization :: every member gets its default right in the field declaration. The constructor only mentions what differs. Ideally a defaulted constructor for systems.
- Scalars :: with equals: i32 x = 5;
- Aggregates :: equals plus designated initializers: Vec3 v = {.X = 1.0f, .Y = 2.0f};
- Constructors :: init lists > initialization in the body. Initializing in the body is not forbidden due to certain language specifics, but it is not preferred.
- explicit :: mandatory on single-argument constructors.

ZII: design every type so that all-zeros is a valid state — that's what default constructors are for.

Memory:

All memory is allocated up front: one OS allocation is immediately split into allocators and arenas — at minimum general purpose and frame. Memory may be allocated additionally at runtime, but not for a specific object — rather in batches for a specific situation, and again not just anywhere, but in one place. STL containers remain allowed. Custom templated allocators or containers from std::pmr::* may be used.

- Two primitives :: Heap - general purpose allocator, lives for the whole program, for objects created once that live for the program's lifetime, or objects recreated rarely. Arena - Push, Reset, optionally Tag and Restore.
- An object in an arena :: trivially destructible, or destroyed by an explicit loop before the arena reset.

** Memory flow

An object's initializer receives only the allocators that outlive it. Everything else is requested as a parameter when needed: an object does not hold anything whose lifetime differs from its own.

Example:
#+begin_src cpp
class Renderer {
  // ...

  void Init(Heap *allocator, Arena &scratch);
  void RenderFrame(Arena &frame);
}
#+end_src

This yields an interesting semantic — allocators stored inside an object are passed by pointer, since a reference member cannot be assigned after initialization.
And objects that are not stored are passed by reference.

** Lifecycle

Three kinds of types:

- Data :: passive aggregates — created in batches in arenas/pools
- Meaningful objects :: constructor or factory establishes the invariant, an invalid object does not exist. Factories return values, not pointers.
- Subsystems :: explicit Init/Shutdown cycle. Banning copy/move is desirable.

Subsystem rules:

1. The constructor only lays out fields as zero-values. A subsystem is considered invalid without Init. Calling Init twice in a row is a programmer error, but Init -> Shutdown -> Init is fine
2. Shutdown is idempotent: it releases only external resources. Memory is not freed piece by piece but cleared in one place by the allocator.
3. Subsystem methods assert IsInitialized (method or field) — a half-alive state is legal, but guarded.

* Formatting
- Indentation :: spaces. Width 4.
- Braces :: K&R
- Column limit :: none, clang-format does not intervene, but try to stay within 120.
- Pointers and references :: attached to the name: const Vec3 &v, PlayerID *p
- Const before the type :: const foo &, not foo const &
- Namespaces :: contents without extra indentation

* Files

- File names :: PascalCase after the main class, extensions are .h and .cpp, we don't use .hpp.
- Include guard :: #pragma once

* Modules

Code is split into flat modules; there are no nested submodules. Module = folder = build unit. Folders are PascalCase.

Inside a module:

- Public :: public contract — headers visible to external code.
- Private :: implementation — .cpp files and internal headers. Never lands on the include path.

** Canonical include

A public header physically lives at <Module>/Public/<Project>/<Module>/<Header>.h, while the module's Public directory itself is added to the include path. The include line is therefore always canonically full:

#+BEGIN_SRC cpp
#include "<Project>/<Module>/<Header>.h"
#+END_SRC


** Dependencies

- A module depends only in one direction. Cycles between modules are forbidden.
- All platform-specific code lives inside its own module and faces outward only through an interface.

* Macros

Naming: SCREAMING_SNAKE_CASE.

Philosophy:
- constexpr for compile-time constants
- macros only for real codegen.
